## 一、目标②：选轨手动入口的残留风险（R1–R3）

### R1 `hidden` 属性被 `.fc-btn` 压掉：选轨按钮全端常显，选完轨就是死按钮 ⚠ 高（一行修，合入前必修）
- **现象**：`dashboard.html` 给 `#careerPickBtn` 写了 `hidden`，`renderCareerPickBtn`
  也在切 `btn.hidden`——但 `screens.css:478` 的 `.fc-btn { display: inline-flex; }`
  是作者样式，按层叠规则**压过 UA 样式表的 `[hidden] { display: none }`**。
  结果：按钮从首帧起对**所有玩家、所有视口**常显；`needsPick` 为假的玩家
  （绝大多数存档）点它走 `maybeOfferCareerTrack` 的早退 `Promise.resolve(false)`，
  什么都不发生——工具区里躺着一颗永远点不动的「选择职业轨道」。
  这不是猜测：本库为同一坑已经打过**六处**补丁
  （`fc-contract.css` 的 `.fc-contract-hud__btn[hidden]`、`fc-gameplay.css` 的
  `.fc-saga-banner[hidden]` / `.fc-tabpanel[hidden]` / `.fc-goal-hud[hidden]` /
  `.fc-drawer[hidden]` / `.fc-alloc[hidden]`，全是 `display:none !important`），
  唯独新按钮没配。更糟的是三层掩护：G1 的断言只查源码里有 `hidden` 字样
  （`r18-stale-contract.test.js:58`，全绿）；§41 已勾 `[x]`；O5 的派工措辞是
  反向的「窄屏**可见**」——按钮现在到处可见，O5 一看「可见」达标就可能写
  skip 笔记收工，把 bug 留在版本里。
- **建议护栏**：`fc-gameplay.css` 加一行 `#careerPickBtn[hidden] { display: none !important; }`
  （O5 的可写路径，正好是它的活）。合入前用 P1 手测验一次「已选轨存档看不见按钮」。

### R2 点遮罩 / Esc = 自动签下推荐轨：手动入口把「点开看看」变成不可逆落轨 ⚠ 中
- **现象**：`fc-career.js` 的 `showPicker` 里 scrim 点击与 Escape 都走
  `finish(hint)`，`finish` 的 `resolve(id || hint)` 兜底到推荐轨；
  `maybeOfferCareerTrack` 拿到 id 就 `applyTrack`（`picked = true`，不可逆）
  并写日志「你选择了…」。这套语义在 **boot 自动流**里是可辩护的取舍
  （开局不能留着没选轨的档），但手动按钮复用同一条路后：玩家点「选择职业轨道」
  只是想看看三条轨长什么样，点遮罩退出——轨道已经替他签了，按钮消失
  （修完 R1 后），没有任何确认步骤，也没有反悔入口。「手动入口」的立项理由
  是把选择权还给玩家，现在的关闭语义恰好把它又拿走了。
- **建议护栏**：小修——`maybeOfferCareerTrack` 手动调用时传个
  `{ manual: true }`，picker 在该模式下 scrim/Esc `resolve(null)` 且调用侧
  对 null 不 `applyTrack`（按钮还在，下次再选）；不修则 §41/KNOWN 落字
  「关闭选轨面板视同接受推荐轨」，并给推荐卡上的「推荐」角标加一句副文案。

### R3 守卫分支 resolve(null) → 日志印出「你选择了「null」轨道作为起点。」 ⚠ 中（正常玩法可达）
- **现象**：`showPicker` 有三个守卫分支直接 `resolve(null)`：picker 已开、
  `FC.events.isOpen()` 为真、`tracks()` 为空。而 `maybeOfferCareerTrack` 的
  then 回调不检查 null：`applyTrack(run, null)` 静默落**推荐轨**（`picked=true`），
  日志模板 `"你选择了「" + id + "」轨道作为起点。"` 直接把 **null 打进正文**。
  两条新增的可达路径都来自手动按钮：其一，**toast 在屏时点按钮**——toast
  占用 `current`（`fc-events.js:718`）但注释明说「不进 FC.overlay：不锁滚动
  也不抢焦点」，页面完全可点，`isOpen()` 却为真；其二，**双击/双触**——
  `picker` 变量在 Promise executor 里同步赋值，第二击命中守卫，
  在第一个面板还开着时就把轨落了、按钮藏了，玩家随后在面板里点的选择
  只是覆盖 track 字段再记一条日志。结果都一样：没见过面板、轨道已定、
  日志里躺一行「null」。
- **建议护栏**：与 R2 同一刀——then 回调对 null 早退（不 applyTrack、不写日志）
  即可同时修掉两条路径；这比给每个守卫补日志文案便宜得多。

## 二、目标①：过期门禁重验销账的残留风险（R4、R6、R8）

### R4 重验是全量门禁：合约还活着、只是进度漂移，卡也被当「过期」永久销掉 ⚠ 中（落字或收窄，二选一）
- **现象**：`pendingContractStale` 复用 `meetsContract`，它验的不止
  「id 相符且 active」，还有 `requires` 的 `progressMin/Max`、`monthsLeftMin/Max`
  区间。五张现役门禁卡里：EV93/EV95 无 requires、EV94（hukou，progressMin 40）
  的进度=edu×0.35+points 基本单调、EV96（home，monthsLeftMax 18）随时间只会更满足
  ——都安全；**EV97（promote，progressMin 45）不安全**：promote 进度里 KPI 占 45 权重
  （`contractProgress`，kpi/70×45），KPI 是月月浮动、会跌的数。可达路径：
  KPI 高位抽到 EV97 → dismiss → 几个月摸鱼 KPI 回落 → 下次进门
  `progress < 45` → 卡被销、`once` 抽卡时已烧、**永久丢**——而合约明明还 active，
  这张卡此刻确认了照样入账。sysLog 说「过期了」、教学第④步说「已经结算或失效」，
  都没覆盖「活合约 + 进度漂移」这种销法；将来 pack 作者加带窗口的门禁卡，
  踩中面会更大。O1 的函数注释倒是诚实（「进度跑出了区间」写在设计意图里），
  所以这可能是有意的取舍——但取舍要落字。
- **建议护栏**：二选一。收窄：stale 判定只查 `ctx.id !== ev.contract || status !== "active"`，
  区间漂移放行补弹（反正入账口 `creditContract` 自己有 active 判定兜底）；
  落字：§41/KNOWN 写明「重验含进度/期限区间，漂移出区间的挂账卡同样作废」，
  且教学第④步的「结算或失效」补半句（见联动节）。

### R6 月中敲门路径的销账吞掉当月抽卡额度：注释的承诺只在 boot 路径成立 ⚠ 低
- **现象**：`replayPendingModal` 里的注释说「销掉过期合约卡时返回 false：
  这一步没弹窗，不该占掉本轮的敲门额度」——boot 链确实按返回值分流
  （false 不置 `replayed`，后续自动流照跑，正确）。但月结路径
  （`dashboard-app.js:1555`）是 `if (hasPendingModal()) return replayPendingModal(silent);`
  ——**不看返回值直接 return**，销账的那个月既没有补弹也不再走
  `drawModalEvent`，当月危机/O1 供给静默停一拍，下月自愈。影响很小
  （安静一个月甚至未必是坏事），但代码注释承诺的语义与一半调用点不符，
  下轮有人按注释推理就会误判。
- **建议护栏**：顺手修是把月结路径改成 `replayPendingModal(silent).then(shown => shown || 走抽卡)`；
  不修就把注释改成「boot 路径不占额度；月结路径销账即当月静默」。

### R8 销账日志不点卡名、时点滞后：dismiss 半年的玩家对不上号 ⚠ 低
- **现象**：sysLog 固定文案「那张合约相关的通知过期了，不再补弹。」——
  不带事件标题。销账发生在**下一次进门或下一次月结**，离合约结算可能隔了
  数月；对一张 dismiss 过很多次的卡，玩家未必记得「那张」是哪张。另外
  `run.log` 上限 60 条，这行解释可能在玩家看到前就被冲掉。教学第④步承诺的
  「日志里留一行说明」成立，但说明的可读性一般。
- **建议护栏**：文案带上 `ev.title`（「‘积分窗口’那张通知随合约结算作废了」量级）；
  一行改动，与 R4 的落字口径一起定。

## 三、目标③：教学 KEY 增量不 bump 的残留风险（R5、R7）

### R5 不 bump 政策的首案恰好是「行为变了」的文案修正：旧读者留着旧承诺 ⚠ 中（政策补一档 + 落字）
- **现象**：这次修文案的动因不是措辞打磨，而是 O1 把补弹行为改了——
  「刷不掉也丢不了」从真话变假话。按 SOP §6 第 1 条走不 bump，代价是：
  **v7 已读玩家（恰好是逐字读过旧承诺的人群）永远不会被动看到修正句**，
  除非自己点「新手教学」重看。他们撞上销账时的全部解释链是 R8 那行不点名的
  syslog。政策本身是对的（R17-R7 三轮三 bump 必须刹车），但 SOP §6 的两档
  （增量不 bump / 结构性才 bump）中间漏了一档：**「行为语义变化驱动的文案修正」**
  ——既不是措辞微调（旧文案已经是错的），也够不上结构性改版（步骤/锚点没动）。
  本案是首个判例，不落字的话下轮遇到同类还要再吵一遍。
- **建议护栏**：SOP §6 补第 5 条：行为变化令旧文案失真时默认仍不 bump，
  但**必须**同轮补两件事——游戏内即时提示（本轮的 syslog 算达标，按 R8 提升可读性）
  + DISPATCH/KNOWN 里记「旧读者认知偏差窗口」。§41 也补一句「已读玩家不重看，
  靠系统日志兜底」。

### R7 两处旧文案残留：文件头注释与第③步过宽句 ⚠ 低
- **现象**：其一，`fc-guide.js:9` 的 KEY 旁注释还是旧语义
  「v7：带『合约』标签的城市事件也挂账，确认前刷新会原样补弹」——正文改了
  注释没改，下轮有人按注释理解 v7 就会把修正句当 bug 改回去。其二，
  第③步的「抽到的城市危机/事件弹窗也要选完才算数：确认前刷新的话，
  进门会再弹一次同一张」是无条件承诺，对合约门禁卡已不为真——第④步的
  限定句救得回来，但只读③不读④的玩家拿到的仍是旧世界观（R16-R12 点过
  这句对 saga 也过宽，本轮适用面又大了一圈）。
- **建议护栏**：注释一行改掉（O3 半分钟的事）；第③步句尾加「（合约类见下一步）」
  或续档 KNOWN。

## 五、教学「丢不了」措辞联动对表（R17-R12 的回收与新账）

第④步现行句：「日志里打『合约』标签的城市事件…要看合约还在不在：合约还在
进行中，没确认就刷新，下次进门原样再弹一次；合约已经结算或失效了，那张门禁
通知就自动作废，日志里留一行说明，不会再补弹。」逐半句对表：

| 教学承诺 | 现码行为 | 判定 |
|---|---|---|
| 「合约还在进行中…原样再弹一次」 | 合约 active 且 id 相符**且 requires 区间仍满足**才补弹 | ⚠ 半真：EV97 的进度漂移销卡不满足「还在进行中就再弹」（R4）。要么收窄实现，要么句子改成「合约还在、条件也还够得着」量级 |
| 「已经结算或失效…自动作废」 | `status !== "active"` 或 id 不符（换签）→ 销账 | ✅ 为真；「换签」归进「失效」口径勉强成立 |
| 「日志里留一行说明」 | sysLog 固定句，销账时写入并落盘 | ✅ 为真，但不点卡名、时点滞后、log 上限 60 条可能冲掉（R8） |
| 「不会再补弹」 | `clearPendingModal` 先行，二次进门无卡无日志 | ✅ 为真（幂等靠先清后写的顺序保证） |

旧句「刷不掉也丢不了」已删干净（G1 有 `doesNotMatch` 断言），R17-R12 的
主联动**销案**。新账三笔：R4 的半真句、R7 的第③步过宽句与头部注释、
R5 的「旧读者看不到新句」。结论：文案与主行为已对齐，**但「作废」的触发面
比文案宣称的宽**——R4 拍板前这张表别归档。

## 六、选轨按钮可见性专述（含 ≤640px）

**桌面（>640px）**：工具区 `.fc-dash-tools` 六键一行（推进/快进/重开/教学/选轨/地图）。
R1 修复前：选轨按钮对所有人常显。修复后：仅 `needsPick` 档可见，位置在
「新手教学」右侧——与它的功能对仗（两个都是补救型手动入口），位置合理。

**≤640px（`fc-gameplay.css:583` 的媒体查询）**：`#tickBtn` / `#tick6Btn` /
`#resetBtn` 被 `display:none !important` 收进底部行动栏，工具区**保留**
「新手教学 / 选择职业轨道 / 打开城市地图」三键——careerPickBtn **不在**
隐藏名单里，窄屏可见性本身是成立的（O5 若只验这条确实可以 skip，
但见 R1：真正缺的是 `[hidden]` 保护，别验反了方向）。排版账：
按钮缩到 `padding: 8px 10px; font-size: 12px`，三键 + `.fc-rowgap` 的
`gap: 6px` 在 390px 一行放得下；320px 会靠 `flex-wrap: wrap` 折行，
不产生横向溢出。遮挡账：工具区在 AP 条之下、日志滚动区（`max-height: 42vh`）
之上，`.fc-page` 底部预留 `108px + safe-area` 给固定底栏，无重叠。
**结论：≤640px 的问题不是「看不见」，而是（R1 修复前）「该看不见的时候看得见」。**

## 七、回归手测路径（P1–P7）
