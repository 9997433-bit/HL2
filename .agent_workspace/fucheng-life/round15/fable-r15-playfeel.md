## 一、目标①：探区护栏的残留风险（R1–R3）

### R1 `keepZone` 还原救不回已发生的副作用 ⚠ 低（前瞻）
- **现象**：`doAction` 对任何带 `zone` 字段的行动都会消费 `zoneQueue` 并 `queueZoneAftershock`。
  现包只有 `explore` 带 zone，且被 `AUTO_SKIP` 拦死，所以 `autoSpendAp` 尾部的
  `keepZone` 还原纯属保险丝。但将来若 pack 给别的行动加 `zone` 字段，
  自动行动会先触发探区事件 + 排队余波，然后 `zoneQueue` 被「还原」——
  玩家再手动探一次就是**双份余波**。
- **建议护栏**：G1 加一条「pack 内带 zone 字段的行动只有 explore」的守门断言。

### R2 AP 花不完的中止文案指错方向的老病根还在 ⚠ 低
- **现象**：新文案「还剩 N 点行动点花不出去。快进不会替你去探区，探区请自己点」
  只有在**所有非探区行动都不可点**时才会出现——现包 `work` 恒可点（1 AP、无 minLayer），
  这个分支几乎不可达（R14-R8 同源）。一旦未来行动加前置让它可达，
  「探区请自己点」这半句可能与真实原因（比如 AP 面额不够）无关。
- **建议护栏**：保持现状可接受；文案里「探区请自己点」只在 `run.zoneQueue` 非空时拼接更稳。

### R3 手机端读不到「不会替你探区」的承诺 ⚠ 低-中
- **现象**：O4 给 `#tick6Btn` 和抽屉按钮加的 `title` 在**触屏上不显示**；
  抽屉里那行 `<p>` 明文只有打开抽屉才能看到。手机玩家第一次点快进时，
  唯一的告知渠道是 `window.confirm` 的四行文案——而 confirm 在部分 WebView
  被禁用或截断（R14-R6 单点故障未修，本轮 confirm 文案还变长了）。
- **建议护栏**：R6 的 overlay 化仍是正解；短期至少确认微信容器里 confirm 的
  `\n` 多行显示不被截断（见 P1 手测）。

## 二、目标②：现金护栏的残留风险（R4–R6）

### R4 护栏触发无解释，玩家看到的是「快进只会上班」 ⚠ 中
- **现象**：低现金局快进，`pickAutoAction` 连续 9 手 `work`，日志里没有任何一条
  「现金偏低，自动行动切到上班」的系统说明。合约进行中的玩家尤其困惑：
  HUD 挂着落户合约，快进却一手进修都不点——护栏在做正确的事，但没告诉人。
- **建议护栏**：`cashTight()` 首次改写建议时打一条 sysLog（每次快进最多一条），
  O1 可写路径内的小改。

### R5 high 级建议仍压过现金闸，两条「high」互相打架 ⚠ 中
- **现象**：设计上健康见底（<30 rest）与讨债 NPC（network）压过现金闸，
  这两个行动 `d.money` 都是 −1（约一整月收入）。低现金 + 低健康局快进仍会烧钱——
  R14-R2/R3 的亏损螺旋只是收窄（rest 线从 38 压到 30），没有关死。
  另一面：健康 30–38 区间原本会休息，现在被压去上班，低现金局健康**阴跌**，
  连续两轮快进可能把玩家从「缺钱」快进到「缺钱又缺命」。
- **建议护栏**：属设计取舍，但必须写进 §38 的口径（F3/G2 对齐：「现金护栏
  不覆盖健康危机与人情讨债」），否则手测的人会当 bug 报。

### R6 双闸阈值不一致 + 收入侧兜底可能失效 ⚠ 低
- **现象**：sim 闸看「现金 < 月收入」，dashboard 闸看「现金 < 账单合计」，
  谁先触发谁改写，实际生效阈值是两者较大值——行为没错，但排查问题时
  两处日志/断言口径要分清。另外 sim 闸的兜底 `run.income`（上月**净额**）可为负、
  gap 期收入可为 0，此时 `monthly > 0` 不成立、sim 闸静默失效，只剩 bills 闸兜着。
- **建议护栏**：G1 若要断言护栏，请断 dashboard 的 `cashTight` 行为而非只断 sim opts。

## 三、目标③：打断文案的残留风险（R7–R8）

### R7 「被一件事打断」不点名是哪件事 ⚠ 低-中
- **现象**：新文案月数准确了，但打断者是危机、结算、要约还是 saga 没说；
  快进日志洪水（R14-R14 未修，本轮零处理）里，玩家仍要自己翻那张卡。
  快进产出 20+ 条日志淹没关键卡的问题，在概率闸让快进更常走满 3 月后**更重**（见 R18）。
- **建议护栏**：hit 时把弹窗标题拼进文案（「被『合约结算』打断」），一行改。

### R8 开局签约窗快进 = 每月被 picker 敲一次门 ⚠ 中（R14 遗留原样）
- **现象**：月 1–3 快进，`maybeOfferContract` 每月重弹、「再想想」占额度
  → `monthModal` 返回 true → 快进停。开局连点三次快进会被敲三次门，
  R15 只把文案改准了（「快进走了 1/3 月」），连环敲门的节奏本身没动。
- **建议护栏**：与 R14-R13 同判：快进期间跳过 offer、结束后补问；本轮不做就记 KNOWN_ISSUES。

## 四、目标④：结算补弹的残留风险（R9–R14）

### R9 补弹只挂在 boot，本局内没有第二次机会 ⚠ 中
- **现象**：结算卡若被程序性 `FC.events.close()` 冲掉（reset 流程、队列清洗），
  `dismissed=true` → `onApplied` 不跑 → `resolutionPending` 留着，但
  `replayContractResolution` 只在 init 尾部跑一次。玩家视角：合约 HUD 已打 ✓，
  钱没到账，界面上**没有任何入口**主动领，只能靠「刷新一下」这个反直觉操作。
  （已核对：Esc 不会吞卡——`requestClose` 对未作答的卡走 `deny()`，玩家路径安全，
  这条主要防程序性 close 与未来改动。）
- **建议护栏**：`monthModal` 开头顺手查一次 pending（不占弹窗额度，排在结算判定旁），
  或把「刷新可补领」写进 KNOWN_ISSUES。

### R10 旧档的历史欠账一律不补 ⚠ 低（已知限制，要落字）
- **现象**：`migrateContract` 给旧档补 `resolutionPending = false`——R15 之前
  已结算但被刷新吞掉奖励的存档，不会被补弹。方向正确（防双入账），
  但等于对老玩家宣布欠账一笔勾销。
- **建议护栏**：写进 §38 或 KNOWN_ISSUES：「补弹只对 R15 后发生的结算生效」。

### R11 结算月撞结局月：奖惩进不了结局评分 ⚠ 低-中
- **现象**：`finishMonth` 里 `checkEnding` 在 `monthModal` **之前**：合约到期与结局
  同月时，结算卡不弹、奖惩不入账，`buildPayload` 按没领奖的数值算结局分，
  确认结局后 `FC.write({run:null})` 清档——欠账随档消失。挑战档 60 月到期
  与合约 deadline 同月是可复现路径（见 P5）。半个后门：结局 overlay 挂着时刷新，
  boot 会先补弹再继续，反而能把奖领回来——行为不一致。
- **建议护栏**：本轮至少在验收条文里把「结局月结算不保证入账」写成已知边界。

### R12 O3 未落地，双 API 汇合点的语义要在合入时对齐 ⚠ 中（协作风险）
- **现象**：dashboard 的 `contractResolutionPending` 走三层 fallback：
  Sim API（O2，已在树上）→ `FC.contract.needsResolutionReplay`（O3，**还没影**）→
  本地 `!c.resolutionDone`。Sim API 存在时后两层永远是死代码；若 O3 落地时
  给自己的 API 不同语义（例如对旧档返回 true），不会生效但会留下误导性代码。
  `markContractResolutionDone` 则是**三层全跑**（Sim 销账 + contract 销账 + 本地标记），
  O3 若在自己的 mark 里做副作用（比如写日志），会被重复触发。
- **建议护栏**：合入顺序 O2→O3→O1 时明确「判定以 Sim 为准，O3 只做兼容转发」；
  G1 加一条两 API 判定一致的断言。

### R13 教学第④步在教一个错误的恐惧 ⚠ 高（一行改，合入前必修）
- **现象**：O5 已提交的 v5 文案：「确认之前别刷新页面，**这局进度没存盘，
  刷了就得从头开始**」——三处失实：① `render()` 每帧都 `FC.write({run})`，进度一直在存；
  ② 刷新不会从头开始；③ R15 的招牌功能恰恰是「刷新后补弹」。教学与本轮实现**正面冲突**，
  玩家照做会白紧张，不照做会发现教学骗人。
- **建议护栏**：O5 改成「结算卡要点完确认奖惩才入账；万一刷新了，重进会把这张卡补给你」。
  这是全清单唯一「高」级，且改动成本一行。

### R14 教学 KEY v4→v5：所有老玩家被迫重看整套教学 ⚠ 中（需拍板）
- **现象**：`shouldShow` 只认 `fucheng.guide.v5`，R15 上线后每个老玩家进城
  都会自动重弹 5 步教学（boot 链尾 `FC.guide.show()`）。为两句新增提醒
  重放整个流程，对回流玩家是打扰；且重弹发生在补弹结算、选轨、签约之后，
  开局弹窗链最长可达 4 连。
- **建议护栏**：要么确认「重看」是本轮有意为之（新增护栏值得广播），
  要么 shouldShow 兼容 v4 已读、只对第③/④步做角标提示。

## 五、目标⑤：危机概率闸的残留风险（R15–R18）

### R15 实现与派单参数有出入，验收别写死数字 ⚠ 低
- **现象**：派单写「0.45/0.7/1.0」，实现是 since 3–4 同档 0.45、5 档 0.75、≥6 保底 1.0。
  期望节奏约 3.9–4.5 月一次、最坏 6 月必出——符合「约 3–5 月」的叙事目标。
  §38 条文没写死概率数值（好），F3 草稿与 G1 断言也应只锁「可跳过 + 有保底」两个端点。

### R16 危机池塌缩没修：同卡循环从「准点」变「随机」 ⚠ 中
- **现象**：R14-R15 的病根原样——顺风局 eligible 恒 2–3 张、`recentCrisis` 窗 4 大于池子、
  兜底整池回填。概率闸只是把「每 3 月准点同卡」摊成「每 3–6 月随机同卡」，
  重复本身还在，只是不那么像闹钟了。
- **建议护栏**：与 R14 同判：兜底时优先挑 `recentCrisis` 里最老的一张；中期补无条件危机卡。

### R17 危机没有「补弹」待遇，刷新吞卡 + 去重回滚仍在 ⚠ 中-高
- **现象**：R14-R17 原样：`noteCrisis` 抽中即记（玩家应答前）、`lastCrisisMonth`
  仍由 dashboard 在 `drawModalEvent` 设（双主体）；危机卡挂着时刷新，
  这两个内存变更没落盘（上次存档在 `finishMonth` 的 render，弹窗之前）→
  当月危机被吞，且同 id 下窗口可立即重抽。**新增的期望差**：R15 教会了玩家
  「刷新后合约结算会补回来」，玩家会自然推断危机也守恒——实际不然，
  体感从「bug」升级成「双标」。
- **建议护栏**：§38 措辞把补弹范围收窄到「合约结算」（G2 现稿已如此，保持）；
  KNOWN_ISSUES 明记「危机/O1 弹窗不补弹」；中期给危机做同款 pending。

### R18 快进更常走满 3 月 → 静默扣款与日志洪水权重上升 ⚠ 低-中
- **现象**：概率闸前「快进三月几乎必被第 3 月危机打断」（R14-R16），现在约 55% 概率
  连 since=3 的月份都直接滑过——快进静默走满 3 月成为常态。R14-X1 的
  「自动行动扣钱 + 探区余波 + 月结账单」三连静默扣款、R14-R14 的日志洪水，
  这两个未修问题的**曝光频率**因此上升。护栏做对了，账单更难对了。
- **建议护栏**：优先做 R7（打断点名）+ 快进月度摘要日志，成本低收益直接。

## 七、回归手测路径（P1–P8）

> 与 G2 `R15_TEST_NOTES.md` 六景互补：那边验「功能对不对」，这边专打上文风险点。
> 环境同 G2：`python3 -m http.server 8000`，清站点数据，开 Console。

- **P1 探区保全专项**：地图选 `auction` → 快进 → 任意方式中断 → 检查
  `locChip` 与 `apHint` 仍显示探区目标、Console 里 `run.zoneQueue === "auction"`；
  再手动点「探区」确认事件正常触发且只排一条余波。盯防：R1。
  顺带在手机视口确认 title 提示不可见时抽屉明文可达。盯防：R3。
- **P2 低现金快进观感**：Console `run.money = 0` → 快进 → 日志应 9 手全 `work`
  （或 health<30 时穿插 rest）；记录「无解释条」的观感与是否会被当 bug。盯防：R4、R6。
- **P3 低现金 + 低健康螺旋**：`run.health = 32; run.money = 0` → 连续快进两轮 →
  记录健康曲线（预期：一路 work 阴跌，<30 才切 rest）与现金/负债变化。盯防：R5。
- **P4 补弹幂等三连**：合约推到到期（改 `run.contract.deadlineMonth = run.months`）→
  tick → 结算卡弹出**不确认** → 刷新 → 应补弹 → 确认 → 记下 `run.money` →
  再刷新 ×2 → 不再弹、钱不再动、`run.contract.resolutionPending === false`。盯防：R9、§38 幂等。
- **P5 结算撞结局**：挑战档把 `run.challengeMonths` 与合约 `deadlineMonth` 调到同月 →
  tick → 记录结算卡是否被结局吞、结局评分是否含奖惩；再试「结局 overlay 挂着时刷新」
  的补弹后门。盯防：R11。
- **P6 教学回归**：localStorage 只留 `fucheng.guide.v4` → 进城 → 确认教学自动重弹
  （老玩家视角计一次打扰）；逐字读第④步文案，与 P4 实测的补弹行为对照。盯防：R13、R14。
- **P7 危机节奏统计**：顺风局（健康/社交/债安全侧）连推 12 月 × 3 局，记录危机间隔
  分布（预期 3–6 月、6 月必出、不再准点 3 月）与 id 重复率（预期：重复仍在，只是错拍）。
  盯防：R15、R16。
- **P8 危机刷新吞卡**：危机卡挂着 → 刷新 → 重进：预期（现状）当月危机被吞、无补弹；
  连推数月看同 id 是否立即复现。与 P4 对照体验差，确认 KNOWN_ISSUES 措辞。盯防：R17。

## 八、已核对无虞（不占风险名额，防重复排查）
