## 一、目标①：tracksPending 收窄的残留风险（R1–R3）

### R1 过期门禁卡照样补弹：合约没了，卡还在承诺加分 ⚠ 中（落字或小修，二选一）
- **现象**：补弹通道不重验门禁。`meetsContract` 的「合约 active 且 id 匹配才入池」
  只在 `drawModalEvent` 抽卡那一刻检查；`replayPendingModal` 直放 `openEvent`，不再看
  `contractCtx`。可达路径：EV93 挂账 → 玩家月月 dismiss → 合约到期、`tickContract`
  挂 `resolutionPending` → 结算卡先放完（月内或进门皆可）→ **下一次补弹的还是 EV93**，
  一张指着已结算合约的「积分窗口」卡。更疼的是账面：`creditContract` 对
  `status !== "active"` 静默返回 0——EV93/EV94 选项上写的落户加分**一分不入**，
  钱 / 健康 / 人脉却照常入账；EV97 的 `kpi` 无 active 判定，照加。玩家看到的是
  「选项承诺 A+B，实际只给了 B」，还没有任何日志解释为什么。
- **建议护栏**：要么 `replayPendingModal` 里对 `ev.contract` 重验 `contractCtx`
  （id 相符且 active），不合格就销账 + sysLog 一条「那张单子过期了」——注意 `once`
  在抽卡时已烧，销账即永久丢卡，与教学 v7「刷不掉也丢不了」的句子冲突（见 R12），
  两处要一起改；要么 G2/F3 在 §40/KNOWN 落字「合约结算后补弹的门禁卡只入普通账，
  合约加分不再生效」。二选一，不能都不做。

### R2 结算卡判定靠 id 命名约定，pack 作者一脚就能踩穿 ⚠ 低（前瞻）
- **现象**：`isContractResolutionEvent` 的依据是「id 以 `contract_` 开头 **且**
  category 为 `合约`」。这是命名约定不是结构标记：现有 story.json 一百多张事件
  没有一张撞前缀（EV93–97 已逐张核对），但将来任何人往 pack 里加一张
  `contract_xxx` + `category:"合约"` 的普通事件，它就会被静默排除出补弹通道，
  回到 R15-P8 的吞卡老行为，且没有任何测试会红。
- **建议护栏**：`story-schema.test.js` 加一条「事件 id 不得以 `contract_` 开头」的
  约定断言（一行）；中期正解是结算卡带显式 `resolution: true` 结构标记，判定不猜 id。

### R3 合约 O1 现在也吃「月月敲门占额度」：R16-R3 的适用面扩大了 ⚠ 低（落字）
- **现象**：入了 pendingModal 通道就继承它的全部语义——`monthModal` 里旧账不清、
  每月强弹窗名额都被同一张卡消费。合约门禁 O1 全是 `once` 卡、五张里三张带
  进度 / 期限 requires，玩家 dismiss 后它月月重敲，新危机 / 新 O1 供给停摆，
  直到作答。R16-R3 落字时的口径是「危机、O1 与人情讨债」，没把合约系算进去；
  §40 也只写了「会写入 pendingModal 并可补弹」，没写「也会月月敲门占额度」。
- **建议护栏**：G2/F3 把 R16-R3 的 KNOWN 口径补一句「含合约门禁 O1」即可，防手测误报。

## 二、目标②：boot 收敛的残留风险（R4–R7）

### R4 dismiss 也算「补弹发生过」：连续关卡的玩家进门永远只有一张卡 ⚠ 中（落字）
- **现象**：`replayContractResolution` / `replayPendingModal` 一律
  `.then(function () { return true; })`——**弹过就算数，不管玩家答没答**。
  结算卡被 dismiss 时 `markContractResolutionDone` 不跑、待办不清，于是
  连续 dismiss 的玩家每次进门都是：补结算 → 关掉 → 选轨 / 签约 / 教学全跳过。
  教学 v7（新 KEY，人人未读）会一直顺延；签约窗口（月 0–3）的自动流程同样顺延
  ——好在签约有 tick 侧 `maybeOfferContract` 与手动按钮双兜底、教学有手动按钮，
  真正无兜底的只有老档无轨道这种极端情形（`needsPick` 恒真但每次都被跳过）。
  「弹过就算」本身是对的取舍（连弹收敛的立项理由就是补弹后别再排队），
  但 §40 只写了「已完成……补弹」，验收者按字面会把 dismiss 场景当 bug 报。
- **建议护栏**：§40 措辞从「已完成补弹」改成「发生过补弹（含被关闭）」；
  老档无轨道的极端情形记 KNOWN 或让 `maybeOfferCareerTrack` 豁免 skip（同 challenge 例外）。

### R5 boot 忍住了，第一次 tick 又冒出来：连弹变「分期连弹」 ⚠ 低
- **现象**：收敛只管 `init` 链。被推迟的签约，在玩家进门后第一次「推进一个月」的
  `monthModal` 里照常弹（offer 排在 pending 补弹**之前**，命中还会把挂账卡再顺延
  一个月）。玩家的体感时间线是：进门补弹 1–2 张 → 刚摸到仪表盘 → 点推进 →
  签约 offer + 月度事件又来。总弹窗数没少，只是从「进门 6 连」摊成「进门 3 + tick 2」。
- **建议护栏**：属取舍且大概率是对的（tick 是玩家主动动作，弹窗有心理预算）；
  R17_TEST_NOTES 手测记录一条观感即可，别当回归。

### R6 闯城欠账档进门仍是 3 连弹：预期管理要跟上 ⚠ 低（口径）
- **现象**：challenge 例外是对的（没主目标没法计分，防软锁必须问），代价是
  「结算补弹 → 危机补弹 → 主目标选卡」三连仍在。§40 写「当次推迟自动选轨、
  签约与聚光灯教学」，没写「最坏仍有三层」。从 R16 的 6 连降到 3 连是实打实的
  收敛，但拿着 §40 逐字验收的人数出 3 层可能记 fail。
- **建议护栏**：F3/G2 在 §40 或 TEST_NOTES 注明「闯城欠账档最坏 3 连（双补弹 + 主目标）
  属预期」；P3 手测按这个口径数层。

### R7 教学 v6→v7 又全量 bump：三轮三连，政策问题第三次上桌 ⚠ 中（需拍板）
- **现象**：R15→v5、R16→v6、R17→v7。dispatch 这次明说「boot 若跳过教学不升版也行，
  升版则兼容旧键」，O3 仍选了升版——为第④步新增的一句话，全体老玩家重看 5 步教学。
  旧键回填（v6/v5/…）做了、回滚安全，工程面无可挑剔；但 R16-R11 说的
  「每轮 bump 正在成为惯例」如今是既成事实。唯一的缓和：boot 收敛让欠账档的教学
  顺延到了干净进门那次，6 连弹的最坏情形没了。
- **建议护栏**：拍板一个政策并写进 SOP：教学增量默认**不** bump KEY（新句自然出现在
  下次主动打开时），KEY bump 留给结构性改版。别再让每轮 O3 自行选择。

## 三、目标③：危机池扩容的残留风险（R8–R10）

### R8 兜底项漂移：注释说「无属性门槛」，wage_delay 其实带月份门槛 ⚠ 低
- **现象**：`pickMonthCrisis` 的空池兜底取 `MONTH_CRISES[length-1]`，扩容后从
  city_check 漂移到 wage_delay；兜底路径不查任何门槛，而 wage_delay 带
  `minMonths: 7`——O2 注释「末位留给无属性门槛的一条」只对了属性一半。
  实际影响为零：side_or_study（minMonths 3、无属性门槛）自月 3 起恒合格，
  而 `since < 3` 早退保证月 3 前根本走不到抽卡，`pool` 空不了，兜底分支
  是死代码。但「死代码 + 不准确注释 + 会随扩容漂移的隐式契约」三件套，
  下次往尾部加一张重门槛卡时就会变成活雷。
- **建议护栏**：顺手改成显式引用（按 id 找兜底项）或删掉死分支；不改就把注释改准。

### R9 顺风局有效池 ≈ 5 张：明显好转，仍未到「月月新鲜」 ⚠ 低（改善 + 残留）
- **现象**：9 张里 4 张带属性门槛（健康 <58 / <46、负债 >8000、人脉 <55），
  健康富裕的顺风局玩家有效池是 side_or_study / rent_fight / city_check（gap5）/
  family_call（gap4）/ wage_delay 五张——比 R15-R16 记录的 2–3 张循环翻倍，
  `recentCrisis` 窗口 4 配 5 张常轮池，重复率从「必然连庄」降到「偶尔眼熟」。
  新卡三条全押在「钱—身体—家庭」的非工位压力面上，选题方向也对。残留：
  窗口 4 + 有效池 5 意味着顺风局第 5 次危机起仍会开始轮回。
- **建议护栏**：续档即可，本轮不动；下轮若再扩池，优先补 needSocialBelow /
  高负债之外的**顺风局专属**门槛卡（比如高收入才触发的消费陷阱），比无门槛卡更值。

### R10 family_call 的 money -3 是全池最重现金单击 ⚠ 低（数值复核）
- **现象**：「先打钱回去」`money: -3`（经 `moneyOf` 按收入折算即三个月收入量级），
  比池内其余现金项（-1 / -2）都重，换来的 social +3 也是全池最大人情单击。
  写实上成立（「家里能拿出来的全部」的对向呼应），但低收入档月 6 就可能触发，
  一击打掉的现金相当于同期房租危机的两倍；另一头 EV96（家里凑首付给你）与它
  同存档先后出现时，观感是「妈妈的钱进进出出」。
- **建议护栏**：手测 P6 记录低收入档实际扣款金额；若体感过重，把 send 降到 -2
  或给 later 分支加一点缓和（现在是 social-3 + health-3，两头都疼是设计本意的话就落字）。

## 四、横切风险（R11–R12）

### R11 G1 对 dashboard 仍是源码正则，且这轮的断言更「实现形状化」 ⚠ 低-中（流程性）
- **现象**：R15-R19 / R16-R13 同款问题第三轮续档，且形状耦合更深：boot 收敛的断言
  要求源码里存在 `var X = false;`、对 X 赋值 ≥3 次、存在 `if (X)`——重构成
  helper 函数或对象状态就假红（15:07 的 `7555be4` 已经是一次「测试迁就实现」的
  返工，O4 审计也点名过 fixture 评估时漏带 helper 的坑）；`tracksPending` 的
  断言是「函数体内不得出现 `ev.contract`」的负向源码匹配——将来在**函数体内**
  写一行含这个词的注释都会红。行为级空白照旧：补弹恰好一次入账、skip 分流的
  真值表（答 / dismiss × 结算 / 危机）、过期门禁卡（R1）都无行为覆盖。
- **建议护栏**：接受现状（DOM 难 mock），P 系列写进 R17_TEST_NOTES 必测项；
  下轮考虑把 `tracksPending` / `pendingKindOf` 这类纯函数抽到 Sim 侧，让 G1 能 vm 真跑。

### R12 教学「刷不掉也丢不了”与 R1 的任何修法都要对表 ⚠ 低-中（联动）
- **现象**：v7 第④步新句收得很准（「日志里打『合约』标签的城市事件也一样：
  没确认就刷新，下次进门原样再弹一次，刷不掉也丢不了」），当前实现下为真。
  但它与 R1 是联动关系：若按 R1 建议加「过期销账」，`once` 已烧、卡即永久丢，
  这句话立刻变假——改 R1 必须同步改这句。另外 R16-R12 指出的第③步过宽句
  （「城市危机/事件弹窗也要选完才算数」把不补弹的 saga 链式卡也许诺进去了）
  本轮原样保留，saga 依旧不进补弹通道（R16-R6 未动），旧账继续挂。
- **建议护栏**：R1 拍板时把这句教学带上一起改；saga 过宽句续档 KNOWN，下轮
  若做 saga 挂账再回收。

## 五、回归手测路径（P1–P7）

- **P5 dismiss 循环**：结算卡连续 3 次 dismiss（每次刷新重进）→ 每次进门应只有

- **P6 新危机三连发**：Console 分别造 `health=40, months=8`、`months=6`（隔 4 月）、
  `months=7` 强抽 checkup_arrow / family_call / wage_delay（`Math.random = () => 0` 过闸）→
  逐张核对文案排版、入账金额（family_call 的 -3 在低收入档记具体数字）、
  `recentCrisis` 去重与下次不连庄。盯防：R9、R10。
- **P7 教学 v7 重看确认**：v6 已读档进门（无欠账）→ 预期全套 5 步重弹（R7 现状）→
  逐字读第④步新句，与 P2 的过期卡行为对照，确认「丢不了」当前为真。盯防：R7、R12。

## 六、已核对无虞（不占风险名额，防重复排查）

1. **收窄不会误伤现有内容**：story.json 全部事件 id 无一以 `contract_` 开头
   （EV93–97 为 EV 前缀、category 教育/金钱/人情/职场），`isContractResolutionEvent`
   只会拦住 `resolutionEvent` 产物；两处调用点的显式 `{pending:false}` 双保险原样保留，
   删掉任何一道都不会双发。
2. EV93–97 载荷纯 JSON（id / choices / contractProgress / kpi 全部可序列化），
   `presentation` 缺省解析为 modal；`once` 在抽卡时烧掉并与 pendingModal 同一次
   `FC.write` 落盘，补弹绕过 `pick()` 不会二次烧账（O4 审计逐张核对，与本文交叉验证一致）。
3. `creditContract` 对非 active 合约静默返回 0，R1 是观感 / 承诺问题，**不会崩**；
   `applyContractChoice` 的 kpi / property 分支也都有存在性判断。
4. `pendingKindOf` 的 contract 分支已在 `d48b10b` 补上（O4 发现的 npc 误标已修），
   `LOG_MAJOR.contract` 早已存在，补弹日志层色正确。
5. boot 收敛的 `replayed` 是 `init` 内局部变量，不落盘、无存档污染；跳过的自动
